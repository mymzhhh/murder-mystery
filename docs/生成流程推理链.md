## 1. 一个必须先说清的陷阱

「用思维链写作」这个说法在**本项目里**有个反直觉的结论：**不能让模型把思考写出来**。

代码里已经踩过这个坑。`buildOutline` 的 prompt 明文写着：

> **不要输出任何思考过程、推理草稿、分析说明**——直接给出最终 JSON。

旁边的注释解释了原因：deepseek 这类推理模型会先用大量预算"思考"再输出正文，
要求它把思考也打进正文，只会更贵、更难以解析，而且思考文本经常混进交付物。
本项目已经为此专门写了"正文为空则从 reasoning_content 里提取 JSON"的兜底。

所以本方案的做法是：

> **把「思考」变成独立、结构化、可被代码校验的中间产物**，而不是让模型输出思考文本。

"链"体现在产物自身的结构上——机制 → 物理可行性 → 目击条件 → 最弱处 → 证明链——
而不是体现在模型的独白里。

## 2. 改造前的问题（读代码得到，非推测）

| # | 问题 | 证据 |
|---|---|---|
| 1 | 全流程只有 `outline` 一个"思考产物"，且它被明令禁止思考。诡计能不能立住只在一次调用里隐式决定一次 | `buildOutline` 的输出铁律 |
| 2 | **校验发生在生成之后，且失败没有后果**：`checkTrickObservability` 发现"核心诡计在物证上不可观测"时只 `console.warn` + 推一条进度，不回炉、不阻断 | `murder-mystery-builder.js` 的 clues 阶段 |
| 3 | **失败代价极不对称**：任何一步抛错 → `writeScript` 重跑整个 `buildMurderMystery`（`MAX_GEN_RETRIES=2`），所有角色剧本 + 线索 + DM 全部重来 | `script-writer.js` |
| 4 | prompt 要求"关系网必须连通"，但**没有任何代码验证连通性** | 大纲 prompt vs 零校验 |

问题 2 是最要命的：用户可以拿到一个"诡计无法被任何线索证明"的废本，而流程显示成功。
实测反例《钟楼诡影》就发生过——全案只有一口被拨快的座钟，花园那口是停摆的，
唯一能测出时差的怀表没有任何线索卡。

## 3. 实现

### 3.1 新增阶段：核心诡计与证明链（在大纲之前）

```
optimizePrompt
      ↓
writeScript
      ↓
buildMurderMystery
  ├ ★ 阶段 1.2  trick-design      诡计 + 可行性 + 证明链   ← 新增，可校验
  ├   阶段 1    framework         散文框架
  ├   阶段 1.3  outline           锁人数/角色/诡计/时间线（注入上面的诡计为硬约束）
  └   …（阶段 2-5 完全未改动）
```

**出口不变**：最终仍然产出与改造前结构一致的 outline JSON，
所以角色剧本 / 线索 / DM / 交叉校验四个阶段**一行都没改**。这是把风险压到最低的关键。

产物结构（`designTrick` → `validateTrickDesign` 校验 → `trickDesignToText` 注入大纲）：

```jsonc
{
  "type": "时间诡计",
  "coreTrick": "…", "mechanism": "…", "conceal": "…", "breakPoint": "…",
  "dependsOnClock": true,
  "feasibility": { "physics": "…", "witness": "…", "weakest": "…" },
  "proofChain": [
    { "clue": "客观描述的读数/痕迹/原话", "kind": "independent-time-source", "proves": "让玩家能推出什么" }
  ]
}
```

### 3.2 确定性校验（这套方案的可信度所在）

校验必须是**代码**，不能是"再叫一次 LLM"——否则只是用一次不确定的判断去校验另一次不确定的输出。
规则（`validateTrickDesign`）：

- 必填字段与最短长度：`coreTrick` / `type` / `mechanism`(≥30) / `conceal` / `breakPoint`
- `type` 必须在 6 种枚举内
- `feasibility` 三问齐备：物理可行 / 目击条件 / 最弱处
- `proofChain` ≥ 3 条，每条 `clue` ≥ 10 字、`kind` 在枚举内、`proves` 齐备
- 至少 1 条**玩家伸手就能拿到**的实体线索（`physical-trace` / `testimony` / `record`）
- **线索禁止结论句**：`这证明了…` / `凶手就是…` 一律拒（推断是玩家的乐趣）
- 禁止超自然设定
- **涉及公共时钟时**（显式字段、类型、或文本提到钟表三条信号任一命中）：
  必须同时有 `independent-time-source` 与 `clock-anomaly` 各至少一条

最后一条就是把问题 2 的**事后警告变成事前约束**。

### 3.3 分级修复：让校验有后果

| 档位 | 场景 | 处理 |
|---|---|---|
| 可局部补丁 | 线索缺独立时间源 / 时钟异常 | **定向补写 1-2 条线索**并复检，不重跑 40-50 条的线索阶段 |
| 需重跑单步 | 诡计设计本身不合格 | 只重做这一个几百 token 的小步骤（带具体错误反馈） |
| 需整体重跑 | 人数不符等 | 保持原有行为 |

补写线索的**插入位置很关键**：必须落进「第二轮线索」区间。
解析器（`extractAllClues`）按 `## 第X轮` 切区间、再按 `### B12：` 取条目，
落错轮次等于这条线索**在游戏里根本不会被发出来**——补了等于没补。
所以有 `insertCluesIntoRound2`，并且用**真实解析器**做测试（见 4.2）。

### 3.4 降级路径

诡计阶段全部尝试失败时 `design = null`，流水线**继续走**，只是不注入诡计硬约束。
改造前没有这一步也能出本子，所以必须保持同样的可用性下限——
新增步骤绝不能把整条流水线搞挂。失败原因会带进进度消息（管理端可见），
而不是只丢在容器控制台里。

## 4. 验证

### 4.1 单元测试（25 项，`tests/unit/trick-design.test.js`）

覆盖每条校验规则，**包括反向用例**（合规设计必须通过——防止规则误伤导致每次都重做）。
重点几条：

- `停摆的钟不能充当独立时间源`——钉住《钟楼诡影》那个实测反例的产品结论
- `未显式声明 dependsOnClock，但文本提到钟表时同样按时间诡计要求`
- `involvesClock 不把「分钟」误判成时钟`
- `insertCluesIntoRound2`：**用真实 `extractAllClues` 解析**，断言新线索落进第二轮；
  另有一条断言"存在第三轮标题时仍落在第二轮、且 C1 没被挤走"

全量：`npm test` → **468 / 468 通过**（改造前 443，本次 +25）。

### 4.2 真实模型烟雾测试（`_verify/trick-smoke.js`）

单元测试只证明校验器；烟雾测试回答另一个问题：**真实模型能不能产出通过校验的设计**。

一次调用只有几百 token，比跑完整本子（10+ 次大调用）便宜得多。结果：

| 用例 | 结果 | 证明链 |
|---|---|---|
| 时间诡计 | 首次通过 | 7 条：`clock-anomaly` + 2×`independent-time-source` + 2×`record` + 2×`physical-trace` |
| 密室 | 首次通过 | 8 条：`physical-trace` / `record` / `testimony` / `independent-time-source`，**没有被误加时钟要求** |

产出质量符合设计意图，例如时间诡计那条给出的证明链是：
巡捕房到场记录（怀表按天文台标准时校准）、医院验尸记录（依尸僵/尸温推定死亡时间）、
电报局回执戳记、座钟柜铜锁孔新划痕、拨针钥匙手柄沾新钟油、账房《上局簿》记录、
凶手房中搜出沾机油的白手帕——全部是客观可获取的物证，没有一条是结论句。

### 4.3 一个被烟雾测试抓出来的性能缺陷（已修）

第一版给 `maxTokens: 4096`，日志立刻暴露：

```
[generate] reasoning 占用预算致正文为空，升级 max_tokens 4096 → 8192
                                                8192 → 16384
                                               16384 → 32768
```

推理模型把预算烧在思考上，触发**四次递增升级**，单次调用膨胀到 **251 秒**（全在空转重试）。

修法照抄大纲阶段已经验证过的结论：一次给足 `24000` + `noEscalate: true`，
正文为空时由"从 reasoning_content 提取 JSON"兜底。实测：

| | 修前 | 修后 |
|---|---|---|
| 时间诡计 | 251.6s | **86.1s / 122.8s** |
| 密室 | 146.3s | **44.0s / 54.8s / 72.3s / 91.3s** |

### 4.4 已知限制（如实记录）

- **非确定性**：temperature 0.8 下观察到一个用例两次尝试都未通过校验（约 6 次里 1 次）。
  该次失败**降级路径工作正常**（不崩、管理端有提示），但**我没有抓到那一次的具体校验错误文本**，
  因此无法判断它是偶发还是某个提示词维度的系统性问题。已把失败原因前两条推进进度消息，
  后续可从管理端日志观测。
- **耗时**：诡计阶段本身是额外一次调用（约 45-125s）。它的收益是省掉整线重跑，
  但**我没有做"改造前后整本生成总耗时/总 token"的对照测量**，所以不能声称净收益。
  这是下一步该量的东西。

### 4.5 端到端验证被一个**框架阶段**缺陷挡住

跑完整流水线时，**第一个阶段（故事框架）连续 3 次尝试全部失败**：

```
[framework] 生成失败: 模型仅在推理后未输出正文（reasoning 占满 32768 tokens 预算）
经过3次尝试，剧本生成仍失败：故事框架生成失败: …
trick 阶段是否出现：✖ 否
```

约 16 分钟烧在 3 次整线重跑上，新增的诡计阶段**根本没机会执行**。
框架阶段执行在我新增的阶段之前、代码我也没有改动，所以这是**既有缺陷**，
但它挡住了本方案的端到端验证——必须一并处理。

> **⚠️ 更正（补记）**：那次 E2E 是**在本地**用 `node _verify/pipeline-e2e.js` 跑的。
> 本地进程连的是本地 Redis（注册表为空）→ `getActiveConfig("generative")` 回退到环境变量
> → `deepseek-v4-flash`。而**容器里的 generative 通道实际生效的是 `opencode-omen-alpha`**。
> 也就是说，那次 E2E 并没有复现生产环境的模型配置。
> 后续实测（4.7）表明：**换模型不能解决这个问题**——见下。

**根因推断（后被实验否定）**：框架模板开篇要求模型「先在脑中敲定核心诡计，确保其逻辑自洽、物理可行」，
而框架自身又要求产出作案动机 500 字以上 + 双时间线表格 + 关系网连通性 + 一二层平面布局。
对一个推理模型来说，这是一次巨大的"自我一致性校验"，于是预算被思考吃光。

**与本方案的关系**：诡计已经由阶段 1.1 定稿并通过确定性校验，
框架阶段那段"自己设计并验算诡计"的推理就是**纯浪费**。
所以新增阶段的正确接法不只是"多一条约束"，而是**同时卸掉下游的重复推理**。

已实现的处置（`buildFrameworkPrompt` 新增 `trickDesign` 参数）：

1. 诡计设计注入框架的用户消息；
2. 把模板里的「创作顺序纪律」整段替换为「**核心诡计已定稿，禁止重新设计**——
   不要重新构思、不要自行推演或验算可行性、不要改动机制」，只保留"围绕它构思人物"和"最后填时间线"；
3. 为让顺序成立，**诡计阶段从框架之后移到框架之前**（先想清楚再写）。

### 4.6 ❌ 上面的假设被实验否定（如实记录）

对照实验（`_verify/framework-smoke.js`，同一输入、唯一变量=是否注入，各一次真实调用）：

| 用例 | system | user | 结果 |
|---|---|---|---|
| A 不注入（改造前行为） | 2231 字符 | 235 字符 | ✖ 正文为空（332.1s） |
| B 注入已定稿诡计 | 2223 字符 | 940 字符 | ✖ 正文为空（299.6s） |

**两者以完全相同的方式失败**（`模型仅在推理后未输出正文（reasoning 占满 32768 tokens 预算）`）。
所以「取消框架阶段的自我设计指令」**不是**这个故障的解因——我的推断是错的。

但这个失败结果本身给出了更有价值的线索：

- prompt 只有 2231 + 235 字符，**根本不大**，模型却把 32k token 全烧在思考上、正文一个字不输出；
  这不是提示词内容问题。
- 同一模型、同一天，**本方案新增的诡计阶段连续多次成功**（86~250s，输出完整）。
  两者的差别是**产出的体量与形态**：诡计阶段要的是约 600 token 的紧凑 JSON，
  框架阶段要的是 3000+ 字、且带"诡计→人物→时间线"全局自洽约束的长篇散文。

### 4.7 框架阶段的真实用途（决定修复方向）

查代码得到，`report.framework` 的下游用途是：

| 用途 | 位置 | 是否兜底 |
|---|---|---|
| `era` / `location` / `victim` 正则提取 | builder 516-521 | **总是使用**，且直接 `.match()`，为空会崩 |
| `extractLayoutPlaces`（线索发现地点） | builder 593 | **总是使用**（与大纲地点合并，大纲在前） |
| 组装成稿的章节文本 | builder 276 / 1791 / 1870 | **总是使用** |
| 角色提取 / 蓝图注入 | builder 468 / 536 | **仅兜底**（大纲缺失时） |

而代码注释明确写着：

> framework 初稿的角色名/凶手/时间体系可能与大纲锁定后的最终设定不一致（历史发生了"柳寒山vs陈风"
> "素心vs小翠"污染）；因此 **framework 只用于组装成稿，绝不再注入生成 prompt**

**结论**：框架阶段被要求产出 500 字动机 + 双时间线表格 + 关系网连通性 + 一二层平面布局，
但它的产物实际只被当作**元数据 + 排版素材**使用，创造职责早已由大纲阶段（和新的诡计阶段）承担。
它要求的工作量远远超过它在下游的实际作用——这既是最容易崩的一步，也是最该瘦身的一步。

### 4.8 真正的解因：换生成模型（实测数据）

既然框架阶段是最难的一步，就用它当试金石逐个实测候选模型
（`_verify/test-model.js`，原生 https、与应用同样的 180s 超时判定）。
判据有两个：**能不能出正文**，以及**能不能在应用 180s 超时内返回**。

| 模型 | 耗时 | 正文 | 推理 | finish | 结论 |
|---|---|---|---|---|---|
| **glm-5.3-flash** | **91.8s** | **6618 字符** | 5022 字符 | stop | ✅ **可用**（六章节齐备） |
| omen-alpha | 87.4s | 0 | 60574 字符 | length | ✖ 预算被推理吃光 |
| mimo-v2.6-flash | 254.9s | 0 | 56944 字符 | length | ✖ 同上，且超 180s |
| longcat-2.5-preview-free | 246.7s | 0 | 20925 字符 | length | ✖ 同上 |
| step-5-preview-free | 1.9s | — | — | — | ✖ 429 端点不可用 |
| deepseek-v4-flash | — | 0 | — | length | ✖ 同上 |

规律很清楚：**失败的模型都是"推理不封顶"**——`reasoning_content` 写到 2 万~6 万字符，
把 `max_tokens` 整个吃光，`finish_reason=length` 且正文为空。
可用的 `glm-5.3-flash` 推理量是**有界的**（5022 字符）然后就落笔。

参数与网关（`https://opencode.ai/zen/go/v1`，需 `x-opencode-session` 头）都已注册在
`scripts/register-opencode-models.js`；切换用应用自己的 `setActive`：

```bash
docker exec murder-app node -e "require('/app/src/llm/model-manager') \
  .setActive('generative','opencode-glm-5.3-flash').then(r=>{console.log(r);process.exit(0)})"
```

**即时生效、无需重建容器**（`getActiveConfig` 每次读 Redis，只有 2s 合并窗口）。

> 一个方法论教训：我第一版测试脚本用 `fetch`，两次调用都恰好停在 **306s** 报 `fetch failed`，
> 我差点把 `glm-5.3-flash` 误判成不可用。实际是 **undici 的默认 `headersTimeout` 是 300s**，
> 是我的客户端在掐，不是网关。改成原生 https（与应用同路径）后才拿到真实结果。
> 凡是"慢"的接口测试，先确认超时是哪一层的。

### 4.9 端到端最终验证（容器内、生产环境）

切换后在容器里跑完整流水线（`docker exec` + `E2E_ROOT=/app`，用容器的 Redis 与 PG）：

```
[+4.4s]   <trick> 正在设计核心诡计与证明链（第 1/2 次）...
```

## 6. 借鉴外部方案后的加固（三锁 / 维度 / 时代 / 轮次）

对照社区里几个剧本杀生成项目后，补了四条**确定性**规则。选它们的标准是同一条：
**能写成代码校验的才要**——提示词里已经写过但没人执行的规则，等于没有。

参考：`gloria-yin/MYSTERY_ENGINE`（动机-手法-机会三锁、双轨时间线、突破线索链、双阶段解锁）、
`klren0312/script-kill` 的 `jubensha-gen`（JSON schema 与硬性要求）。

### 6.1 三锁齐备 + 线索按「支撑维度」归类（改动最大的一条）

改造前 `proofChain` 只校验**条数**和 **kind**，不问"这条线索推得动哪一维"——
凑够 3 条全是物证、**动机零支撑**也能过。后果是玩家能把人送进去，却说不清"为什么是他"。

现在每条线索必须声明 `supports`（`motive` / `means` / `opportunity` / `timeline`），并强制：

- **三锁各至少一条**支撑线索（动机/手法/机会缺一即打回）
- 涉及公共时钟时，**额外要求**至少一条 `timeline` 支撑
- 非时间诡计**不要求** `timeline`（有测试专门防这条误伤）

这条把 builder 里"只对时间诡计检查可观测性"的局限也从**设计阶段**补上了：
手法可行性在诡计阶段就有物证对应，不再等写完 40 条线索才发现。

#### 6.1.1 一次由本改动**引入**的回归（身份诡计），已修

三锁上线后的一次身份诡计复验里，诡计阶段**整段降级**：

```
[trick-design] 第 1 次校验未通过（1 项）：proofChain[2].supports「identity」非法，必须是：motive / means / opportunity / timeline
[trick-design] 第 2 次校验未通过（1 项）：proofChain[2].supports「identity-motive」非法，必须是：…
[trick-design] 全部尝试未通过校验，降级继续（本次生成不注入诡计硬约束）
```

**原因**：身份诡计里玩家要证明的不是"谁有动机"，而是"谁是谁"，
所以模型自然地把线索的支撑维度写成 `identity`——而我的枚举里**没有这一项**。
两次尝试都被打回，最后**整个诡计阶段被丢弃**，这一整类本子都拿不到诡计约束。

这是"严格枚举 + 重试 + 降级"三者叠加的典型风险：一个不完备的枚举，
后果不是"少一条约束"，而是**整段功能失效**。

**修法两条**：

1. **补上 `identity` 维度**，并且只在 `type === "身份错位"` 时**要求**它
   （与"时钟诡计要求 timeline"同构）；其余诡计不要求，避免误伤。
2. **容忍复合值**：实测第 2 次尝试写的是 `identity-motive`（模型想同时表达两个维度）。
   新增 `splitSupports`，把 `identity-motive` / `motive／opportunity` 这类写法拆成多维度按多项计——
   复合值是合理表达，不该因格式问题连续失败。

**教训**：枚举型校验的"非法值"必须区分两种情形——**真的写错了**，与**我的枚举不够全**。
前者该打回，后者该补枚举；而"重试 + 降级"会把后者放大成一整类功能失效。
所以每次新增枚举，都要问一句："这一类本子里，模型最自然的写法是什么？"

### 6.2 可观测性校验推广到**所有**诡计

改造前 `checkTrickObservability` 只在能解析出时钟偏移时触发（`buildTimeAxis` 非空），
非时间诡计直接 `needed=false`——**密室/身份诡计的线索体系哪怕一条物证都没有也照样通过**。

现在：任何有诡计的剧本都要求至少一条**可得锚点**（物证痕迹/记录/证词），
时钟诡计在此基础上**再加**独立时间源与时钟异常两项。

> ⚠️ 这是**契约变更**，`tests/unit/time-axis.test.js` 里那条"非时间类诡计不参与校验"的旧测试
> 已按新契约改写（原断言 `needed=false` 现为 `needed=true`、空线索判不足）。改动是刻意的，不是回归。

### 6.3 时代载体校验（防"民国本子写出联网日志"）

时代在 outline 里只是个自由文本字段，**没有任何东西约束线索载体**——
模型完全可能在民国本子里写出"联网日志""门禁后台导出""微信记录"。

新增 `detectEra` + `checkEraCarriers`：按时代档位（民国/古代）匹配一张**保守的**穿越词表，
违规即走就地改写（`repairClueTexts`），把"联网日志"改成"门房登记簿"这类时代内等价物。

词表刻意保守，并有测试钉住**不误伤**：民国本里的怀表/账本/当票/更夫证词不算违规；
现代/架空时代**完全不检查**（误伤成本 > 收益）。

> ⚠️ 词表在复验时被**收窄过一次**，原因值得记：初版让「古代」档额外禁止
> 电报/报纸/火车/轮船/电话/汽车，看起来合理——但 `detectEra` 会把**清末**
> （光绪/宣统）归入「古代」，而这些东西在晚清**真实存在**
> （电报局、《申报》、淞沪铁路、轮船招商局）。照那条规则会把正确内容改坏。
> 区分"唐宋"与"晚清"需要更细的时代判定；在拿到可靠依据之前，
> **宁可漏报不可误伤**——漏报只是少一次自动修正，误伤是主动破坏正确内容。
> 现在两档共用同一张"二十世纪后期才可能出现的载体"表。

### 6.4 轮次解锁校验（第一轮不得点名真凶）

借鉴"最低解锁=可指控 / 完整解锁=无法抵赖"：两轮发放制的意义在于
**第一轮只能让人起疑、第二轮才能定案**。改造前 clues.js 只写了"单条不得直接指认真凶"
（单条级），但**集合级**没人管——第一轮里直接点出真凶姓名，两轮制就形同虚设。

新增 `checkRoundUnlock`：① 第一轮线索不得出现真凶姓名；② 第二轮必须有定案锚点
（独立时间源/验尸/决定性物证）。①违规即就地匿名化改写（改为身份/关系指代）。

### 6.5 新引入的修复原语：就地改写

6.3 / 6.4 修的是**措辞**而不是"缺内容"，所以不能沿用"补写线索"的做法
（那会新增线索、打乱条数与轮次）。新增 `replaceClueBlock` + `repairClueTexts`：
按线索编号**原地替换**，编号、轮次、条数全部不动。

配套踩到一个 JS 正则陷阱并已修：结尾断言用了 Python 的 `\Z`，
而 JS 里 `\Z` 只是字面量 `Z`，导致**最后一条线索块永远提取不到**。
正确写法是 `(?![\s\S])`，测试里有一条专门覆盖"最后一块"。

### 6.8 复验中发现的实现缺陷（已修）

第一次端到端复验的日志暴露了我自己的一个错误：

```
[builder] 第一轮线索匿名化：就地改写 7/7 条（A2 A16 A25 B14 B23 B24 B25）
```

**改写范围混进了 B 打头的第二轮线索**。我的检查只看第一轮区间
（`checkRoundUnlock` 里用 `第X轮` 标题切片是对的），但接线处统计违规块时用了
`extractClueBlocks(全文)` —— 于是**第二轮线索被一起匿名化了**，
而第二轮本来就该能点名定案，这等于白白削掉定案证据。

修法：让 `checkRoundUnlock` 直接返回 `r1Blocks`（只含第一轮区间内的违规块），
接线处不再自行全文扫描——单一事实来源，避免两处口径分叉。
新增 2 条单测钉住这个行为（"第二轮点名不算违规"、"r1Blocks 只收第一轮"）。

## 7. 状态转折：权威时间轴自身的一个错误

这是三次端到端复验里**反复出现**的那类硬伤（"座钟拨快时刻矛盾"每一轮都在），
追下去发现根因不在角色、也不在框架阶段，而在**为防这类问题而建立的权威时间轴本身**。

### 7.1 现象

交叉校验原文（第一次复验）：

> 座钟拨快时刻矛盾：设定与沈砚清剧本均明确拨快发生在案发当日20:10，但陆延祚剧本写
> '案发当日18:30到大厅，座钟指七点一刻（快45分钟）'……两处都在拨快之前座钟就已快45分钟，
> 与诡计运作原理直接冲突。

### 7.2 根因：把"恒定偏差"写成了全天成立

`buildTimeAxis` 给出的规则是：

```
- 案发当日，公共时钟（大厅座钟）比真实时间快 45 分钟：**座钟时间 = 真实时间 + 45 分钟**。
| 真实时间 | 座钟显示 | 事件（DM 权威） |
| 18:30 | 19:15 | 宾客陆续到大厅 |
| 20:10 | 20:55 | 拨快大厅座钟 |
```

它把偏差描述成**恒定状态**，从不说座钟是**几时**被动的手脚。
于是角色写 18:30 的场景时，照着这条规则写出"18:30，座钟显示七点一刻（快45分钟）"——
**完全符合时间轴，却与诡计直接冲突**。更糟的是对照表把拨钟之前的每一行也套上了偏差，
等于用一张"DM 权威"表**主动教角色把拨钟前的场景写错**。

**复现**（`_verify/axis-tamper.js`，改造前的输出）：

```
| 18:30 | 19:15 |   ← 座钟显示 19:15，但拨钟要等到 20:10
| 19:40 | 20:25 |   ← 同样错
```

### 7.3 修法：把拨钟时刻建模为状态转折

1. 新增 `findTamperMoment`：找出"时钟被动动手脚"的时刻。
2. 时间轴显式写明**转折前后的不同状态**：
   - 拨钟**之前**：座钟读数 = 真实时间，且"不得出现拨动机芯的痕迹、新划痕、工具痕迹
     ——那些痕迹在动手之前还不存在"；
   - 拨钟**及之后**：才出现偏差。
3. 对照表按转折点**分段渲染**：拨钟前的行显示"与真实一致"，之后才显示偏移。

修后（同一输入）：

```
| 18:30 | 18:30（与真实一致） |
| 19:40 | 19:40（与真实一致） |
| 20:10 | 20:55 |
| 21:00 | 21:45 |
```

### 7.4 第一版修复：生效了，但不够（重要的中间结论）

第一版把分段模型写成**对上面那条恒定偏差的补充例外**，恒定公式仍留在头条并加粗。
端到端复验的结果很说明问题——交叉校验原文：

> 核心诡计自相矛盾：**设定集要求座钟在20:50前走时正常**、岑国维20:50逆拨35分钟后钟面显示20:15。
> **但岑国维自己写17:40时钟已慢一刻钟**；且周曼仪/林淑芬在20:00起就观测到慢35分钟…

也就是说：

- ✅ **修复确实生效了**——交叉校验在引用设定集时，复述的正是新加的"20:50前走时正常"这句；
  而且有一名角色（方志诚写 18:00 座钟准确）确实照做了。
- ❌ **但角色整体仍然违反**：真凶写 17:40 就已慢 15 分钟、两名角色从 20:00 起按"慢35分钟"记录，
  全都早于 20:50 的拨钟时刻。

**根因在措辞的位置与权重**：第一条醒目的加粗公式仍是**无条件**的恒定偏差，
分段说明排在后面當例外——模型锚定在头条那条上。规则正确不等于规则有效。

### 7.5 第二版：让分段模型本身成为头条

改动只有三处，但都是冲着"模型会锚定哪一句"去的：

1. **把分段声明提到第一条**，恒定偏差公式降级为"及之后"那一支；
   没有转折点时（`findTamperMoment` 返回 null）才退回原来的无条件写法。
2. 语气从"说明"改成**禁令**：拨钟前"绝对不得写座钟快了/慢了 N 分钟、不得让角色发现座钟不准"。
3. 补一张**可照抄的读数示例表**（拨钟前两行两侧相同、拨钟后两行带偏移）。
   光有规则没有样例时，模型仍会按恒定偏差自行推算。

配套加了一条**守住位置**的测试：断言时间轴的**第二行**就是分段声明、
且头条里不得出现无条件的恒定偏差公式——防止以后有人把它挪回后排。

### 7.6 中途一个被否证的做法（如实记录）

第一版 `findTamperMoment` 用"**离动手动词最近的时刻**"，加一个 ≤8 字的距离阈值。
它在一个测试上失败，追下去发现**距离根本分不清两类时刻**：

实测大纲写「凶手提前将大厅的落地座钟调快约15分钟。**当座钟显示21:30**（晚餐结束）时，
真实时间仅21:15。」——离"调快"最近的时刻是 **21:30**，但那只是表盘**读数**，
真正的拨钟时刻是时间线里的 **19:45**。放宽阈值就会稳定取错，收紧阈值又漏掉
"拨快……的动作发生在20:10"这种动词在前的句式。

**改法**：用**模式**而不是距离——
- 模式 A：时刻紧邻动词（`20:10拨快`、`在20:10拨快`）
- 模式 B：动词在前、动作时刻在后（`拨快……的动作发生在20:10`）
- 反向排除：识别"显示/指着/停在"这类**读数句式**，其中的时刻不是动作时刻
- 都匹配不上则回退到大纲时间线里描述拨钟的那一条；再没有就返回 null，
  **时间轴退回改造前行为（宁可不说，不可说错）**

### 7.7 验证

- 单元测试：`tests/unit/time-axis.test.js` 新增 11 项（`minutesOf` / `findTamperMoment` 四种
  取值路径 + 读数排除 + 分段渲染 + **头条位置** + 读数示例 + 无转折点时的向后兼容），
  全量 `npm test` → **506 / 506**
- 复现脚本转为验收脚本（`_verify/axis-tamper.js`）9 项全过

## 8. 共享事实（改动 3 的预防面）

第 7.9 节列出的三类残留问题（死亡时间冲突 / 角色时间线整体错位 / 同一事件三个版本互斥）
都不是"时钟状态"问题，而是**各角色没有共享同一份事实**。本节做其中**能被确定性代码兜住**的两件。

### 8.1 为什么原来的做法拦不住

角色提示词里其实已经有一张"真实时间 | 座钟显示 | 事件（DM 权威）"的大表，
死亡条目也在其中。但**它在表里没有任何特殊地位**——模型不会自动把其中一行
当成一条不可违反的禁令。实测表现：基准写明 19:20 已身亡，某角色照样写
"20:00 死者还在给我下指示"，并以此为整段情节的前提。

同理，每个角色并不知道**哪些时刻属于自己**。时间线条目写"林晚到31楼送文件"，
别的角色没有任何条目可锚定，就只能自己编——于是"全程用座钟报时但事件时刻对不上基准"。

### 8.2 做了两件事

**① 死亡时刻抽成独立禁令**（`findDeathMoment` + `buildSharedFacts`）

从权威时间线里抽出死者死亡的真实时刻，注入**每一个**角色/NPC 提示词，
写成一条硬约束而不是表格里的一行：

```
- **死者「陆峥」的死亡时刻是 19:20（真实时间）**：19:20 之后，**任何人（包括你）都不得再与死者互动**
  ——不得听见他说话、不得看见他走动、不得与他交谈或交接物品；发现尸体必须发生在 19:20 之后。
```

⚠️ 抽取时必须**排除"发现尸体/报案"那一条**——它的描述里同样含"尸体"字样，
但那是**发现**时刻而不是死亡时刻，混用会把禁令的时间界整体推后。

**② 每个角色的权威时刻锚点**（`characterAnchors`）

把时间线里**点名了该角色**的条目单独摘出来，作为他"不能改动的锚点"注入他自己的提示词：

```
- **以下权威事件提到了你，这些时刻是你不能改动的锚点**：
  - 19:35　林晚到31楼送文件
  - 20:30　林晚发现陆峥尸体并报警
```

这样角色不必从全局表里反推"哪几条与我有关"，也就没有"自己编一个时刻"的空间。

### 8.3 配套的生成后检测

预防不能保证 100% 生效（第 7.4 节已经证明过一次"规则正确但模型不照做"），
所以再加一层确定性检测 `checkVictimAfterDeath`：逐行取时刻，检出
**死亡时刻之后仍与死者互动**的行。

命中后走与 `ensureTimelineComplete` 同构的修复：带明确纠正指令重写一次，
**只有违规数减少才采纳**（否则保留原稿，避免越改越差）。

#### 8.3.1 一次**误报**事故（重要，已修）

第一版判据是"行内同时出现死者姓名与互动动词"，并刻意排除了"看见/发现"二字。
我以为这样就不会误伤发现尸体的情节——**错了**。

实测（清光绪·身份诡计那一轮）6 个角色里有 4 个被判违规，**每人都恰好 1 处**。
"每人恰好 1 处"这种规整形态本身就可疑，于是把真实剧本抽出来逐行核对，抓到的 3 处是：

```
23:30 … 听见霍青在正院方向喊起来 … 常伯衡跪在供桌前     ← 命中「喊」
23:30 … 我叫他，没应。上前摸，人已经凉了 …               ← 命中「叫」
```

全是**发现尸体**的情节。我漏了两件事：

1. 发现现场**必然**有"喊起来""我叫他""惊呼"；
2. 死者在这些句子里是**别人动作的宾语**、或被描述成"跪在供桌前、一动不动"的尸体，
   根本不是"死者活动"。

**代价是实在的**：4 个角色被误判并进入无谓重写（日志里 3 个"重写后违规未减少，保留原稿"，
剩下 1 个"改成功了"也只是把情节改坏）。**误报比漏报有害得多**——
漏报只是少一次自动修正，误报会主动破坏正确内容，还白烧调用。

**修法：把动词锚定在死者姓名之后**（`victimActs`）——死者必须是一行的**动作主语**
（"常伯衡吩咐我…"）才算，而不只是"被提到"。修后拿同一份真实剧本复测：**3 处 → 0 处**，
同时真违规仍然抓得住（"陆峥接了个电话后对我说" → 命中）。

### 8.4 验证

- 单元测试：`tests/unit/shared-facts.test.js` **15 项**（死亡时刻抽取的四种情形、
  排除发现行、锚点归属、禁令文本、检测器的违规/生前/发现尸体/无姓名/跨午夜五种边界），
  全量 `npm test` → **521 / 521**
- 渲染核对（`_verify/shared-facts-demo.js`）：用最后一次端到端的真实数据渲染，
  禁令文本与"林晚专属锚点"都正确，检测器精准命中实测那种违规（20:00），
  且不误伤 19:05（生前）与 20:30（发现尸体）
- 端到端见 8.5

即 6.1 节的三锁/时钟两锁校验在真实生成里**真的拦住了不完整的设计**，不是纸面规则。

#### 仍然存在的问题（如实记录）

同一轮交叉校验的 16 个问题里，剩下的仍是**别的类**：

1. **日期系统错位**：某角色把牌局标"十四日"、把 00:10 标"十五日"，全篇错位一天。
2. **物件状态矛盾**：书房灯"未熄/虚掩"与"里头没点灯"冲突。
3. **同一事件的多方时刻打架**：一个人送参汤，三个角色给出的时刻差 35 分钟。

本轮只做了死亡时刻与角色锚点，物件状态与事件对齐**仍未做**（见第 9 节）。

### 8.6 权威事件表：必须与时钟解耦

追第 8.5 节那三类问题时发现一个更基础的缺口。**复现**：

```
parseTimeOffset → null
buildTimeAxis 长度 → 0
```

`buildTimeAxis` 只在能解析出**分钟级时钟偏差**时才产出（`parseTimeOffset` 返回 null 就整段为空）。
而像"买通更夫漏敲三更"这类诡计**根本没有分钟偏差**——于是角色**拿不到任何权威事件表**，
各方对同一事件的时刻各说各话。这正是"一个人送参汤，三个角色给出差 35 分钟的时刻"的成因。

**修法**：抽出 `buildEventTable(outline)`，与时钟**完全解耦**，只要有时间线就注入：

```
## 权威事件表（所有角色共同遵守 — 同一事件只能有一个时刻）
| 时刻 | 事件（DM 权威） | 涉及角色 |
| 22:50 | 周慕堂用镇纸击杀沈慎之 | 周慕堂 |
| 23:20 | 白玉茹送参汤到书房廊下，见门虚掩 | 白玉茹 |
| 00:40 | 牌局散场，顾小舟去账房对账 | 顾小舟 |
```

两个设计点：

1. **「涉及角色」列由名字匹配确定性算出**——这解决"我该在哪个时刻出现"的问题：
   角色不必从全局表里反推哪几条与自己有关（这些行由 `characterAnchors` 单独给他）。
2. **规则写成"同一事件只能有一个时刻"**，并明确"若你当时在现场而未被点名，
   你的时间线也必须在该时刻出现对应条目，不得自己另给一个时刻"——
   直接对着"多方时刻打架"这个症状。

### 8.7 跨午夜日期规则

第 8.5 节的第一类问题是**整篇日期错位一天**：某角色把案发当日牌局（21:00、22:30）
全标成"十四日"，把 00:05/00:10 标成"十五日"，而设定集里案发夜是"十五日夜至十六日凌晨"。
既有的"统一日期""禁止自创"措辞挡不住这种**整体位移**。

- **事件表里写明分界**：跨午夜时说明"00:00 之后的时刻属于案发次日（即 X）；
  17:00–23:59 属于案发当日；**禁止把整段夜间事件统一标成同一天**"。
- **`nextDayLabel`** 做日期 +1（中文与阿拉伯数字都支持）；
  天数 ≥ 28 时**故意返回 null**——二月没有三十日，"三十日"是否成立取决于月份与闰年，
  宁可不给也不给错。
- **`checkDateLabels` 配套检测**，但只保留两条**没有误伤面**的规则：

  | 规则 | 判据 |
  |---|---|
  | A | 00:00–05:59 的时刻标成当日/案发当日 → 违规（应为次日） |
  | B | 17:00–23:59 的时刻标成次日/案发次日 → 违规（午夜前不可能是次日） |

**一次被我自己拦下的误伤**（值得记）：第一版还加了"夜间事件的日期必须等于案发当日"。
演示脚本立刻打出误报——`十二月十四日 20:30 在报馆核清样` 是**前一日**的正当情节，
上一日的晚间事件标上一日的日期本来就是对的。判别"这一行是案发夜还是前情"需要语义理解，
**代码不该猜**。于是删掉该规则，改为：规则 A 命中时**附带推断**——
"把午夜后标成案发当日，通常意味着整篇日期整体错位了一天，请一并检查夜前事件的日期"。

**但删掉那条规则又放过了一个真 bug**：紧接着的那轮复验里，某角色把整条时间线写成
"腊月十九/二十/廿一"，而设定集是"腊月初八"——与其余五人（初七/初八/初九）完全错位，
交叉校验把它列为头号问题。**这正是我删掉的那条规则本该抓到的形态。**

补救的判法（规则 C）：**只判"晚于案发当日"的具体日期**。

- 早于案发当日的具体日期**不判**——它很可能是正当的前情（"初五那天他来过"），代码分不清；
- 晚于案发当日、又不等于案发次日的日期**必判**——**案发夜之后没有正当情节**，
  出现它只能是日期整体位移。实测那条"腊月十九"（12月19）> "腊月初八"（12月8）→ 命中；
  而"腊月初五"不命中。

配套踩到两个正则坑（都已修）：`腊月初八` 里的 `初/廿/卅` 不在数字字符类里导致整个匹配失败；
以及中文日期有 **`腊月初八`（无"日"）** 与 **`十二月十五日`（有"日"）** 两种写法，
结尾的"日"必须可选。

  且确认**不再误伤** `十二月十四日 20:30` 这类前情行
- 端到端见 8.9

### 8.9 端到端复验（三轮，容器内生产环境）

这一节前后跑了三轮，每一轮都改掉了上一轮暴露的问题——**三轮合起来才说明这一节是否成立**。

| 轮次 | 题材 | 结果 | 这一轮暴露的问题 |
|---|---|---|---|
| ① | 1935 天津·身份诡计·刀伤 | `ok=true`，但**诡计阶段整段降级** | 三锁枚举缺 `identity`（见 6.1.1）→ 已修 |

另做独立核对：把两份真实剧本都过一遍检测器，**均为 0 处违规**。

### 8.10 仍然没解决的：事件表的覆盖边界

第 ③ 轮剩下的 10 个问题**全是同一类**：**关键公共事件不在权威时间线里**。
典型一条：

> 苏韵秋上楼时间互相矛盾：顾行舟称18:30…；苏砚生称…约19:00；郑慕桥称18:30…；
> 阿蘅称"宴未散便先上楼"——上楼时刻与携带物（黑漆账匣/蓝布账本/青布包袱/一册账）
> **四种说法不一致**。

**诊断**：事件表只能对齐**大纲时间线里确实存在的事件**。而"某角色某时刻上楼、手里拿着什么"
这类**角色级公共事件**根本不在 `timeline` 里——于是每个角色各自编一套，
谁也不知道别人写的是什么。

这不是"规则没写清"，而是**权威数据缺失**：要解决它必须让大纲阶段产出更细的公共事件表
（每个关键时刻、每个角色的公开位置/携带物）。这属于**生成侧**的改动，本轮未做。

结论：**改动 3 的"共享事实"做到了"大纲已有的事实不被违背"，
但还没有做到"该有的公共事实一定有"**——后者是把 `timeline` 从"DM 关键节点"扩展成
"角色级公共事件表"，是下一步。

### 8.11 角色级公共事件表：让"该有的公共事实"一定存在

8.10 的诊断落地了：**权威数据缺失**必须在生成侧补上，而不是继续在校验侧加规则。

**新增大纲字段 `publicEvents`**（与 `timeline` 分工明确）：

```json
{ "time": "19:00", "actor": "苏韵秋", "place": "绣楼三层",
  "doing": "携黑漆账匣上楼，未再下楼", "who": ["钱妈"] }
```

- `timeline` 仍是 **DM 关键节点**（凶手何时动手、何时发现尸体）；
- `publicEvents` 是**角色级公开行踪**：谁、何时、去哪、手里拿着什么、谁在场。
  大纲提示词里明确要求「**每一次角色在场景之间移动都必须列一条**」，
  并限定「**只写公开可见的行为**」——不写凶手的秘密动作、不写只有本人知道的内心。

**三个设计点**：

1. **公开性是硬约束**：这张表按构造就是"所有人都能看到的信息"，因此可以安全地
   注入给每个角色（对比 `outlineToText` 里含凶手真实时间线，那是靠模型"知道但不说"）。
2. **可以定向补齐**（`ensurePublicEvents`）：大纲阶段只调一次、没有重试循环，
   而模型未必产出足够的条目。所以校验不达标时**补一次小调用**（只输出 JSON 数组，
   把"缺什么"明确告诉它），合并后复检；**永远不因此让流水线失败**。
   实测演示里它能准确指出"郑慕桥、阿蘅、柳拂云没有任何公开事件"。
3. **锚点核对只告警、不改写**（`checkPublicEventAnchors`）：检查"当事人是否在自己的
   剧本里写出了该时刻"。**故意不做重写**——"当事人未必逐条复述自己的每次走动"，
   缺失不等于错误；把它当硬约束就会重演 8.3.1 的误报事故。
   时钟诡计下角色可能写【座钟】读数，所以真实时刻与换算后的钟面时刻**都算命中**。

4. **禁止凭空给他人安排行踪**（注入规则）。实测里最顽固的一类冲突是
   "角色给**别人**安排了表里没有的行踪"：交叉校验原文——
   "贺掌柜20:00称在账房见秦少棠一人在拨算盘…但秦少棠时间线当晚根本不在账房"。
   表不可能穷举"每个人对每个人的每次目击"，但可以禁止**无依据地把某人的身份
   安在某个时刻某个地点上**：表里没有的，只能写"账房里亮着灯，有个人影在拨算盘"，
   不得断言"那人是某某"。

#### 8.11.1 又一次误判：把**死者**当成名单外的幽灵人名（已修）

第一次跑通时日志报"2 条的 actor 不在角色名单内（如「苏鹤年」）"，
我据此加了"丢弃名单外当事人"的过滤——**然后按惯例去核对产物，发现自己判错了**：

```
- **姓名与身份**：苏鹤年（裕丰茶号东家）
九月十四午后，苏被发现闷死于茶仓麻袋堆后……
```

**苏鹤年就是死者。** 三处判断全错：

1. `rosterNames` 只取 players+npcs，**不含死者**——而死者的行踪
   （"东家独自进茶仓查货"、"钥匙苏鹤年随身不离"）**恰恰是公共事件表最该收录的内容**；
2. 剧本里"苏鹤年"出现 56 次，我一度读成"幽灵人名污染了剧本"，
   实际那只是**死者被全篇提及**；
3. 我那条"过滤修复"**会把死者的合法公开行踪整条删掉**，比不修更糟。

**修法**：`rosterNames` 纳入死者。并留下一条测试专门钉住
"死者的公开行踪不算违规、必须保留"。

> 教训：**看到"异常值"先问它是谁，再决定是不是 bug**。
> 这已经是本轮第三次"检测器误报"（死亡检测器、日期规则、名单过滤）——
> 三次都是**规则写得比事实更绝对**。凡是把"没见过的形态"直接判为错误的地方，
> 都要先去产物里看一眼它到底是什么。

**本轮验证**：单元测试 **559 / 559**（公共事件表相关新增 10 项：净化去重排序、
校验四类不达标、渲染、锚点核对含钟面换算与"非当事人不启用"、死者算合法当事人、
名单外当事人过滤）；渲染核对见演示输出。

### 8.12 端到端复验（1890 广州·白天案，容器内生产环境）

```
[+62.6s]  <trick> 核心诡计已定稿并通过校验：毒在午前凉茶下，凶手伪造午后茶中毒假象…（chain=7）
[+296.9s] <outline> 公共事件表不完整，正在定向补齐：以下角色没有任何公开事件：潘映棠、潘仲衡
[+316.8s] <outline> 公共事件表补齐完成（35 条）
[+316.8s] <outline> 角色级公共事件表：35 条
```

**20.4 分钟出完整 6 人本，诡计阶段首次定稿。** 几个要点：

1. **公共事件表机制全程生效**：初稿 14 条 → **定向补齐到 35 条且达标**；
   死者不再被误判为"名单外当事人"（8.11.1 的修复生效）。
2. **交叉校验 11 个问题**，其中日志可见的前 5 条是：
   日期体系混乱（三份剧本三个日期）、自鸣钟拨快幅度与诡计目的矛盾（拨快两刻=30分钟
   不可能把死亡推后两个时辰）、钟面读数互相矛盾。**没有出现行踪对齐类问题**
   （即"同一趟走动四个时刻四种携带物"那一类）——这正是公共事件表针对的症状。
   ⚠️ 但日志只保留了前几条，**不能据此断言该类已完全消失**。
3. **死亡检测器抓到一次真违规**（不是误报）：

   ```
   - **【怀表】19:40**：账房 — 结当日流水。潘仲衡进来翻了我的进货簿，盯着花梨木那页看了半晌…
   ```

   死者潘仲衡在 19:40（死于午前）还在翻账本。8.3.1 的 `victimActs` 修复靠姓名后紧跟的
   "盯着"锚定命中——**修后仍在真实数据上有效，且没有误报**（对两份真实剧本复测均为 0）。

### 8.13 两个仍未解决的点（如实记录）

**① 死亡类违规的"重写"修复基本无效。** 本轮与上一轮合计：触发 5 次，只有 1 次
把违规从 1 处降到 0（"重写后违规未减少（1 处），保留原稿"出现 4 次）。
原因：修复方式是**整篇重新生成**角色剧本再比对，模型往往会重现同一个错误，而重生成
既慢又可能引入新问题。**更好的做法是像线索那样做"就地改写单行"**
（`replaceClueBlock` 的同构物），但角色剧本是散文结构，改写单行的风险高于线索，
所以本轮没有动——**检测有效、修复无效**这个状态是明确记录的。

**② 一条做了又撤掉的检查（跨角色日期体系）。** 1890 那轮的头号问题是
"三份剧本三个日期"，而我的午夜日期规则在**白天案**上根本不启用。于是加了一条
`checkDateAgreement`：取各角色时间线**行首的"日期+时刻"**，若日期相差超过 1 天即判不一致。

**单测立刻把它否掉了**：角色时间线**本来就要求覆盖"案发前一日"**
（`playerInstruction` 模板明确要求），所以行首必然合法地出现更早的日期——
`- **六月初五 20:30**：报馆 — 他来过一趟`（案发日为六月十四）会被误判成"体系不一致"。
**行首形态区分不了"案发夜"与"前情"**，与 8.7 节那次误伤同一个病根。

于是**撤掉实现、保留放弃说明**（写在 builder 里，避免以后有人再踩），
理由是这一类**已由既有的"交叉校验 → 定向修订"覆盖**：
1890 那轮交叉校验把它列为头号问题，修订阶段应用了 31 条补丁。
**与其再塞一条会误伤的规则，不如让已经工作的机制去修。**

> 本轮（8.6–8.13）一共出现 **4 次**"规则写得比事实更绝对"导致的误判或误伤：
> 死亡检测器把发现尸体判成死后活动、日期规则误伤前一日情节、名单过滤把**死者**
> 当成幽灵人名、跨角色日期核对误伤前情时间线。四次都是**先去产物里看了一眼事实**
> 才发现的。这已经成了这个项目里最该记住的一条工程纪律：
> **凡是把"没见过的形态"直接判为错误的地方，都要先去产物里确认它到底是什么。**

## 9. 按任务清单逐条收尾（10 项）

第 8 节做完后，把剩下的已知问题整理成任务清单逐条修。这一轮完成 10 项（9.1–9.10），
每项都带单元测试；其中多项被端到端复验验证或修正。

### 9.1 死亡类违规：整篇重生成 → 就地改写单行

**问题**：8.3.1 记录过"检测有效、修复无效"——修复方式是整篇重新生成角色剧本，
两轮实测 5 次触发**只有 1 次把违规降到 0**（4 次"重写后违规未减少，保留原稿"）。
重生成既慢（一次整篇 ~60s），模型还常在新稿里重现同一个错误，甚至把别处改坏。

**改法**：与线索阶段的 `repairClueTexts` 同构——**只改违规的那几行**，其余一字不动。
- 新增 `applyLineRewrites(content, oldLines, newLines)`：纯函数，按首次出现精确替换；
- 新增 `repairDeathLines`：一次小调用只改违规行（`maxTokens: 3000`，改不好就整体放弃）；
- `checkVictimAfterDeath` 的违规项改为携带**未截断的整行**（此前截断到 120 字，
  截断过的字符串匹配不到原文，替换会静默失败）；
- `ensureDeathConsistent` 分两级：先就地改写，改不动才回退整篇重生成，两级都失败保留原稿。

**验证**：单元测试 6 项（替换精度/邻行不受影响/同内容只改首次/未命中返回 null/整行保留）。
端到端两次都没有触发死亡违规（本轮各角色都没写出"死者死后仍活动"），
当时如实记为"生产路径的改写分支仍未被执行过"。

> **该未验证项已在 9.9 关闭**。补验时才发现"三轮都没触发"的真实原因不是"没违规"，
> 而是**检测压根没跑**（`findDeathMoment` 的动词表漏了「击杀」等表述，静默返回 null）。
> 修复后构造真违规跑通整链：检测 → 就地改写 → 复检通过，且只改了那一行。
> 详见 9.9。

### 9.2 时钟偏移幅度可行性（设计期校验）

**问题**：实测 1890 广州那轮，设定集称"拨快两刻"（30 分钟）即可让死亡时刻被推后
约两个时辰（午初→未时，2 小时）——**两刻根本不够**，交叉校验事后才把它抓出来。
这类"诡计参数算不通"是设定层的数学错误，写完四万字才发现代价很高。

**改法**：在 `validateTrickDesign` 的时钟分支里加 `checkClockMagnitude`：
- 从手法文本里提取"紧邻调校动词"的时长 = 偏移量（拨快两刻 → 30 分钟），
  与"紧邻伪装动词"的时长 = 声称的时间差（推后两个时辰 → 240 分钟）；
- 单位换算支持 分钟/刻/小时/钟头/时辰，数量词支持中文（两=2、半=0.5、一~九十九）；
- 偏移 < 声称的时间差 → 打回（与三锁、时钟两锁同一套"设计期拦住"的机制）。

判据刻意保守：只比对**紧邻**动词的时长，文本里无关的时长（"死者在书房待了一个时辰"）
不参与比较；两个方向取极端（偏移取最小、声称取最大），宁可放过也不误判。

**验证**：单元测试 7 项（单位换算/实测原文形态报错/偏移够用通过/只提调校不报错/无关时长不误伤/
非时间诡计不触发）。端到端复验时该轮诡计的伪装时长未明确给出数字（"让众人把真实作案时间
集体记晚"），所以未触发——**部分覆盖**，无误伤。

### 9.3 跨角色日期核对：众数投票 + 傍晚窗口

**问题**：8.13 记录过这条检查**做了又撤**（逐条判据会误伤"案发前一日"的合法时间线）。
但 1890 广州那轮的"三份剧本三个日期"确实需要拦——只能由交叉校验事后修。

**改法（重做）**：不逐条判"这个日期对不对"，改为**众数投票**：
- 案发夜在每份角色时间线里都是最密集的一簇（10+ 条），前情只有 1-2 条
  → 取"傍晚时段出现次数最多的日期"作为该案发夜的表达；
- 众数 <3 次视为不可信（薄剧本/前情过多）→ 不参与比对；
- 有权威案发日（`parseCaseDate`）用它，否则用**过半**多数（3-3 分歧不判，交给交叉校验）。

**第一次端到端复验暴露的假阴性（重要）**：1960 云南那轮，岩温把整个案发夜
**整体前移一天**（傍晚在腊月十六，其余五人在腊月十七），交叉校验抓到了，
但我的检查**没触发**——因为总众数只差 1 天，被"跨午夜相邻两天允许"的宽容放过了。

**修法：只统计傍晚（17:00–23:59）时段的日期**。案发夜的傍晚必然属于同一天
（跨午夜只发生在凌晨），所以傍晚窗口下**差 1 天就是整体位移，必须判**；
而合法的跨午夜相邻日（凌晨条目）被窗口排除，不会误伤。

**验证**：单元测试 11 项（众数/前情不影响众数/薄剧本不参与/过半才判/傍晚窗口抓 1 天位移/
合法跨午夜与跨年相邻不触发）。这一轮把"整体前移一天"这个**实测形态**直接做成了测试用例。

### 9.4 关键物件状态变更表（objectStates）

**问题**：8.10 列的"书房灯未熄 vs 里头没点灯""闸板已放下 vs 闸板尚全开"这类矛盾，
根因是各角色对**同一物件在同一时刻的状态**各写各的——timeline 只有事件，没有物件状态的权威来源。

**改法**：
- 大纲新增字段 `objectStates`：`{at, object, state}`，明确要求只写**可被观察到的客观状态**
  （"灯亮着"而不是"灯被凶手调暗了"——后者是秘密动作，属于 `murderer.realLine`）；
- `validateObjectStates` 校验：至少 3 个物件、状态描述不得泄漏秘密动作；
- `ensureObjectStates` 定向补齐（与公共事件表同构：只补一次、失败即放弃、绝不让流水线失败）；
- `buildObjectStateTable` 渲染并注入每个角色/NPC 提示词，规则写明
  **两次变更之间状态恒定**、任何角色同一时刻看到的状态必须与表一致。

⚠️ **只做注入（预防），不做确定性检测**：物件状态是开放的自然语言描述，
用词表匹配必然误伤（本轮已有 4 次"规则比事实更绝对"的教训），检测交给既有的交叉校验。

**验证**：单元测试 5 项（覆盖不足/秘密动作泄漏/合规通过/按时刻排序/空表不编造）。
端到端（1965 长春）**生产验证生效**：`关键物件状态表：10 条`，无需补齐。

### 9.5 轮次解锁：从"出现姓名"改为"结论性指控"（第五次误判）

**问题**：这条检查每一轮端到端都触发匿名化改写（"第一轮线索直接点出了真凶姓名「X」（N 条）"），
我一度以为"每轮都抓到真违规"是好事。直到把产物抽出来**逐条看**（1965 长春那轮）：

```
A1  登记簿显示…借阅人签名栏签有"赵铁成"三字        ← 客观文档列名
A14 赵铁成证词（公开陈述）："我八点差一刻才到澡堂…"  ← 凶手自己的公开说辞
A16 签到簿：…赵铁成19:40（事由栏写"巡检"）        ← 客观文档
A23 赵铁成证词（对质时陈述）…"那钟准不准关我什么事！" ← 同上
```

**全是正当的 PVP 内容。** PVP 剧本里所有人互为嫌疑人，"目击某某出现在某处"
"某人的档案/签到记录"本来就是核心玩法材料——凶手的公开证词更是每个人都知道的东西。
真正破坏两轮制的是**结论性指控**（"凶手就是X""X杀害了死者"），不是提及。

**这是本项目第 5 次"规则比事实更绝对"**（前四次见 8.3.1 / 8.7 / 8.11.1 / 9.3）。
前四次的教训是"先去产物里确认事实"，这次的教训更进一步：
**当一条规则每一轮都"成功"触发时，恰恰要怀疑它抓的是不是真问题**——
一直成功的检测器不一定是好检测器，也可能是一直在误伤。

**改法**：`nameAccuses(text, name)` 只判**结论性指控**——
"凶手/真凶…是X"、"X…就是凶手"、"X…杀害/勒死/毒死…"、"这说明凶手是X"；
纯提及（证词、文档、目击、含凶手字样但不指控）不判。
改写提示词也同步改：明确说明"证词、签到簿这类客观文档里出现名字不算指控，可以保留"。

**验证**：单元测试 6 项（四种指控形态 + 四种纯提及不判 + 空输入），
并把"王管家的证词/签到簿列名"这类**实测原文形态**做成了不判的用例。

### 9.6 无多数派的日期分歧也要报

**问题**：9.3 的众数投票在**无多数派**（如 3-3、4 方各执一词）时直接放行，
理由是"无法确定谁对"。但 1965 长春那轮恰恰是四套日期各 1 票、无多数——

**改法**：无多数派时**仍然报告**（列出各套日期及对应角色），交由修订阶段统一。
无法确定谁对 ≠ 没有问题——分歧本身就是问题，只是修法要交给有上下文的修订阶段。

**验证**：单元测试新增 2 项（1-1 分歧报告、四套日期 + 只写相对日期的角色不参与）。

### 9.8 谜底隔离：角色提示词不再携带"凶手是谁"

**问题（代码审查发现的潜在隐患）**：`outlineToText` 渲染的设定集里有五处**直接写着谜底**——
`### 凶手\n沈砚清，动机：…，手法：…`、`### 核心诡计说明书`（运作原理/隐藏方式/破绽方向）、
凶手真实与伪装双时间线、人物表里的 `【凶手】` 标记、类型行里的"核心诡计："。
而这段文本被**原样塞进了每一个角色与 NPC 的提示词**，只靠一句"不要直接读出真凶名字"维持。

两层代价：
- **单点隐患**：模型一旦漏嘴，扮演该角色的 AI 玩家直接拿到答案，整局作废；
- **更隐蔽的代价**：即使模型守规矩，"知道答案却要装作不知道"也会污染角色行为——
  不敢自由怀疑真凶、下意识避开他、把"无意间说漏"变成不可能。

**改法**：给 `outlineToText(outline, opts)` 与 `buildStructuredSummary(report, opts)` 加
`includeTruth` 开关（缺省 `true`，DM 侧与成稿零改动）：
- 角色/NPC 提示词走 `includeTruth: false`——抹掉上述五处；
- **凶手本人走 `includeTruth: true`**（他要写清自己的真实经过与对外说辞），
  `buildCharacterPrompt` / `buildNpcPrompt` 内部按 `ch.isMurderer` 自动选择；
- `mkBlueprint` 生成两套上下文（`blueprintCtx` 无谜底给侦探/玩家/NPC，
  `blueprintCtxTruth` 含谜底只给凶手），三处消费方（侦探模板、角色、NPC）各取所需。

**判据必须精确（第 6 次「规则比事实更绝对」）**：第一版测试我写成"角色版不得出现真凶姓名"，
立刻失败——**真凶的姓名本来就必须出现**：他就在人物名单里，所有人互为嫌疑人，
"名单里有他"是核心玩法材料（与 `nameAccuses` 的"提及≠指控"同一个病根）。
所以最终断言分两层：① 谜底字符串不出现（动机原文/手法原文/诡计原理/双时间线/`【凶手】`/"动机："）；
② 公共材料仍在（背景/布局/死者/人物名单**含真凶姓名**/关系网/时间线骨架/性格语气）。
每个"不出现"的断言都配了**阳性对照**（DM 版必须出现同一字符串），否则断言会退化成空转。

**顺带修掉的泄漏**：PVE 侦探的提示词原文是
`本案真凶在其中一名NPC中（沈砚清）`——**括号里直接报了姓名**，等于给侦探发答案。

**⚠️ 这件事的性质要说清楚：它是潜在隐患，不是已发生的缺陷。**
用 `nameAccuses` 加"手法原文片段指纹"核查了旧代码生成的那份产物（沈阳·声控灯案，
6 个非凶手角色段落）：**没有一处指控、也没有手法片段命中**。
也就是说，此前 10+ 轮端到端里模型都守住了规矩；这次改的是"不用再靠模型自觉"。
顺手也清掉了 `buildMurderMystery` 里一个死变量 `outlineText`
（三处赋值、全项目无人读取，注解却写着"报告与后续阶段都读它"——失真注解是下次踩坑的种子）。

**验证**：新增 `tests/unit/truth-split.test.js` 9 项（DM 版阳性对照 / 角色版无谜底 /
角色版公共材料仍在 / 摘要两版 / 角色提示词两版 / PVE 侦探 / 缺省值等价 / 空大纲），
全量 **597/597**。所有 `outlineToText` 调用点逐个核对过：补齐类与交叉校验类（内部编辑调用）
与 DM 手册仍用完整版，只有面向角色的三处走无谜底版。

**生产验证（新旧产物双向对照）**：2005 杭州·民宿门禁卡那轮（新代码）`ok=true`、16 分钟、
诡计第 2 次通过、修订 27 条，交叉校验 13 个问题（正常区间，**无退化**）。
用脚本对两份产物做双向核查（旧代码 1990s 沈阳 / 新代码 2005 杭州）：

| | ① 凶手本人有「凶手确认」（阳性对照） | ② 非凶手段落泄漏 |
|---|---|---|
| 旧代码产物 | ✔ 是 | ✔ 无 |
| 新代码产物 | ✔ 是 | ✔ 无 |

① 用「凶手确认」章节是否存在作判据（`script-parser` 正是从该章节抽 `murderer.method`），
比"手法逐字命中"稳健——凶手习惯用自己的话复述，逐字不中属正常（旧产物就是这种情况，
一开始据此误判成"我把该给的也删了"）。

### 9.9 补验 9.1 时抓到的两个真缺陷（死亡保护层）

9.1 一直挂着一条未验证项："LLM 改写 → 替换 → 复检"整链**在生产中还没跑过一次**。
为了闭掉它，我构造了一次真违规去跑真实修复路径——结果第一次跑就发现**检测压根没跑**。
一路查下去是两个独立缺陷：

**缺陷一：`findDeathMoment` 的动词表漏了「击杀」等常见致死表述（静默失效）**

原表只有 身亡/死亡/遇害/被杀/断气/气绝/毙命/死去/咽气/丧命。而这个剧本的时间线写的是
「20:40 谭志强从工具架取铁钩，在站台**击杀**周世奎」——动词不在表内 →
`findDeathMoment` **静默返回 null** → `buildSharedFacts` 里那条
"死者死后不得再与死者互动"的硬约束**整条不注入**给任何角色，`ensureDeathConsistent` 也永不启动。
**三轮端到端"就地改写"从未触发的根因就在这里：不是修复路径不工作，而是检测压根没跑。**
静默失效比报错难发现得多，所以修复分两步：① 动词表补齐（杀死/击杀/击毙/勒死/毒死/刺死/捅死/
砍死/打死/掐死/闷死/淹死/溺死/烧死/电死/摔死/砸死/捂死/坠亡/枪杀/遇刺…）；
② **判不出来时出声音**（进度条 + 控制台告警"本轮死亡约束与死后校验都不会生效"），
让这类失效不再无声。

同时防住一个新引入的误判面：时间线里「19:00 谭志强**决定**杀死周世奎」说的是**打算**，
把它当成死亡时刻会让禁令整体提前、进而把**写对了的**内容判成违规并被改写——
所以预谋/计划行一律不作候选（宁可判不出来，不可判错）。

**缺陷二：`checkVictimAfterDeath` 完全不看日期（实测 100% 误报）**

它的文档串写着"只在同一天内判定"，但实现里只比分钟、没有任何日期维度。于是角色剧本里
「**11月7日** 21:00 周世奎在二楼朝下喊我」这种**案发前一日**的正当内容，
只因为时刻晚于死亡时刻（20:40）就被判成"死者死后仍在活动"，接着会被就地改写**改坏**；
而模板本来就要求角色时间线覆盖"案发前一日"，这类行必然存在。

> 病根与 8.13 的 `checkDateAgreement`、`checkDateLabels` 规则 B 完全相同：
> **代码分不清"案发夜"与"前情"**。这是本项目第三次踩同一个坑。

修法是补一个 `onCaseNight(line, caseDate)` 判据，且刻意**偏向漏判**（改坏正确内容比漏掉一处违规有害得多）：
明确"前一日"→不判；明确"当日/次日/当天"→判；写了具体日期 → 等于案发日才判、
**案发日未知则不判**；没有任何日期标注 → 判（沿用原行为，避免大幅削减检出）。

**量化**（用真实产物，不构造数据）：该剧本 6 个角色段落里，旧判据判出 1 处"违规"——
**就是那 1 处误报（误报率 100%）**；新判据判 0 处，正确。

**验证（闭掉 9.1 的未验证项）**：注入一条能被识别的违规行后跑真实链路：

```
死亡时刻=20:40                       ← 动词表修复生效（此前为 null）
注入后违规数=1
  违规行: - **21:10**：我在站台上碰见周世奎，他说交接单还没核对完，让我先别走。
  正在就地改写...
修复后违规数=0 ｜ 长度 3116→3122（只差 6 字符）
违规行已不在 ｜ 原剧本主体保留 ｜ 未走整篇重生成
✔ 就地改写路径有效
```

⚠️ 这次验证本身也踩了一个坑、值得记下来：第一版注入写成"他还跟我**抱怨**了两句"——
"抱怨"不在 `victimActs` 的动词表内、且隔了十几个字，**根本没被识别**；
那次"检测到 1 处"其实抓到的是产物里那条 11月7日 的误报，**等于没验到注入项**。
**验收脚本的夹具必须与被验判据的口径对齐**，否则会出现"看起来通过了"的假证据。

单元测试新增 8 项（动词表逐个、真实时间线回归、计划行不判、`onCaseNight` 判据、
前一日不误判、同日仍判）；全量 **624/624**。

**9.9.1 第二次漏判，而且是那条告警抓到的**

修完之后立刻跑了一轮真实生成（1998 哈尔滨·冷库），进度里冒出了一句：

```
<player_script> ⚠️ 时间线里识别不出死者身亡的时刻——本轮「死者死后不得再活动」约束与死后一致性校验都不会生效
```

**这正是"判不出来就出声音"那条兜底存在的意义**——它把又一次静默失效变成了可见的。查产物里的大纲：

```
[21:40] 周红梅尾随至三号冷库，以对数为名骗马淑芬入库，用冻硬铁托盘击头致死，掩门离开
```

**"致死"不在动词表里**。我第一版补的是"死亡动词"（杀死/击杀/勒死…），
漏的是一整类**结果补语构词**：X致死 / X而死（中毒致死、失血过多而死、窒息而死）。
补上 `致死|而死|杀害|丧生|殒命|命丧|亡故|毙` 后，同一条真实时间线返回 `21:40`（此前 null）。

> 教训：这张表按"动词"来想总会漏——它还包含**构词**。所以告警兜底不是可选项：
> 两次漏判里，**第二次就是靠它发现的**。词表也永远有边界，与其追求完备，
> 不如保证"漏了会被看见"。

**9.9.2 生产里第一次自己触发（1975 西安·俑坑案，`ok=true`，31 分钟）**

补完构词后跑的那一轮，修复路径**在真实生成中自己响了**（此前三轮一次都没触发）：

```
[builder] 马占魁 死亡时刻校验失败：1 处（死亡时刻 12:15）
[builder] 马占魁 死亡违规行改写后仍有 1 处，放弃改写
[builder] 马占魁 就地改写未成功，回退整篇重生成
[builder] 马占魁 重写后违规 1 → 0 处
```

这一条比构造测试更有价值：**两级分支都真跑了**——就地改写尝试后没改好（如实放弃，
不是硬塞一个"改过"的结果），回退整篇重写把违规从 1 降到 0。
9.1 那条"整链在生产中还没跑过一次"从此**由生产本身关闭**。

**9.9.3 `同刻异地` 之类的判据没做成**（先量后否，见第 12 节）——那是另一个方向，
与本节无关，但同一轮里一起验的。

**9.9.4 第三次漏判 → 改用「死因结构化兜底」，不再靠词表穷举**

补完构词后**下一轮又漏了**（1993 成都·川剧团）。这次的时间线是：

```
[21:10] 贺清源推倒大戏箱压住陈慕舟口鼻，陈怀表摔碎停摆于9:13；库房门锁此刻仍未开
```

**全句没有任何死亡动词**——它只描述了动作本身；而死因字段写的是"被推倒的大戏箱压住口鼻窒息死亡"。
三次漏判（击杀 → 致死 → 无动词）说明：**靠动词表穷举这条路本身就到不了终点**。

所以补了一条**结构化**判据：行内**同时出现死者姓名与死因的实词片段**（且死者不是该行的动作主体、
不是发现尸体行、不是计划行）→ 即死亡时刻。片段从 `victim.causeOfDeath` 现成抽取
（去掉"被/的/致/死亡"等虚词，取 ≥3 字实词 + 4 字窗口——**刻意排除 2 字片段**，太短会到处命中）。

**在全部 4 份真实大纲上测量**（这一步是上线前必须做的）：

| 剧本 | 动词表 | 死因兜底 | 最终 |
|---|---|---|---|
| 2003 重庆·缆车（写「击杀」） | 20:40 | 无 | **20:40** ✔ |
| 1998 哈尔滨·冷库（写「击头致死」） | 21:40 | 21:40（一致） | **21:40** ✔ |
| 1975 西安·俑坑（写「刺死」） | 12:15 | 12:15（一致） | **12:15** ✔ |
| 1993 成都·川剧团（**无死亡动词**） | 无 | **21:10** | **21:10** ✔ 兜底救回 |

**4/4 检出；且在动词表能工作的三份上，兜底的结果与它完全一致（0 冲突、0 误报）。**
补上后该剧本**重新获得**了此前整层消失的保护——实测确认：

```
findDeathMoment = 21:10（此前 null）｜ parseCaseDate = 6月14日
buildSharedFacts 是否注入死亡禁令 = true
  → - **死者「陈慕舟」的死亡时刻是 21:10（真实时间）**：21:10 之后任何人（包括你）都不得再与死者互动…
案发夜 21:30 死者拉住我 → 判 1 处 ✔ ；前一日同一时刻 → 判 0 处 ✔（不误伤）
```

**9.9.5 第四次漏判：时刻字段带日期，`minutesOf` 只认"以 HH:MM 开头"**

修完构词与结构化兜底后，**同一类告警又响了一次**（1994 郑州·打包机案）。这次的原因完全不同：

```
[11月17日 23:50] 王栓柱从背后袭击核对棉垛的陈广发，推入运行中的打包机，陈广发死亡
```

行里**明写着"死亡"**，动词表与兜底都不该漏。问题出在**时刻字段本身**：
那一轮大纲的 `time` 全是 **「11月17日 23:50」**（带日期），而 `minutesOf()` 的正则是
`^\s*(\d{1,2})[:：](\d{2})`——**要求以 HH:MM 开头** → 所有时刻返回 `null` → 死亡时刻判不出来。
顺带还有第二个坑：配套的 `String(t).trim().slice(0,5)` 对「11月17日 23:50」会取成 **「11月17」**。

**改法**：抽出 `hmOf(s)`（从任意位置取规范化的 HH:MM，容忍日期前缀与区间写法），
`minutesOf` 基于它实现；**5 处 `slice(0,5)` 截断全部替换为 `hmOf`**。
单测新增 3 项（日期前缀、中文数字日期、前导零补全、区间取起点、非法值仍为 null、
真实时间线回归）。**用那一轮的真实大纲复验：`findDeathMoment` 从 `null` 变为 `"23:50"`。**

>
> 四次漏判的形态各不相同：**击杀（动词表）→ 致死（构词）→ 无动词（结构化兜底）→ 时刻带日期（解析）**。
> 这正说明"靠单一判据覆盖所有写法"做不到；真正起作用的是那条**"判不出来就出声音"**的告警——
> 四次里有三次是靠它发现的，而不是靠我提前想到。

### 9.10 案发日期：从"事后统一"改为"源头钉死"（根因修复）

**问题（连续两轮实测）**：交叉校验报出的**第一个**问题永远是同一件事——

> 案发日期严重不一致：马占魁剧本为4月16-17日，赵德海为6月14-15日，周素芬为十月十六-十七日，
> 孙佩兰为6月11-12日，李春娥为6月13-14日——同一案件六个角色使用了至少四套不同日期

而修订阶段要为此打 **76 条补丁**去统一。**根因不是"缺少判据"，而是大纲从来没有权威日期**：
`outline` 结构里**根本没有日期字段**，`parseCaseDate` 只能从故事背景/时间线描述里"扫"，
扫不到就返回 null；而 null 会让每个角色收到这条提示词：

> 本案未设定绝对日期：一律使用相对日期表述（案发前一日/案发当日），**严禁自创月份与日期**

**实测证明这条禁令挡不住自创**——六个角色全都自创了，还各创各的。
（与第 8 节反复出现的教训同源：**当"全局唯一事实"没有被钉在源头时，靠事后禁令与修补永远在打地鼠。**）

**修法（源头钉死）**：
1. 大纲 JSON 结构新增 `caseDate` 字段，并在要求里写明**必须给出具体日期**，说明它是全剧唯一时间基准；
2. `parseCaseDate` **优先读这个显式字段**（非法/缺失才回退到原来的文本扫描，保证旧产物不受影响）；
3. 大纲生成后立刻核一次，缺了就**出声音**（进度 + 控制台告警）——不再静默；
4. 下游自动受益：角色提示词从"严禁自创日期"变成"**案发日期统一为「6月14日」**"，
   `checkDateLabels`/`ensureDateConsistent`（跨午夜日期标注）、`onCaseNight`（死亡后活动判据）
   也终于拿到了案发日——此前它们全都因为 `caseDate=null` 而半瞎。

**验证（真实一轮，前后对照）**：1993 成都·川剧团，`ok=true`，21.5 分钟。

| | 修复前（1975 西安·俑坑） | 修复后（1993 成都·川剧团） |
|---|---|---|
| `outline.caseDate` | **字段不存在** | **6月14日** |
| 六个角色的日期 | **4 套**（4月16日／6月14日／十月十六日／6月11日…） | **1 套**（6月13日=前一日，6月14日=当日） |
| 交叉校验的日期抱怨 | **首个问题** | **没有** |
| 修订补丁数 | **76 条** | **19 条** |

单测新增 5 项（显式字段优先、非法值回退扫描、空白归一、中文日期）；全量 **636/636**。

**9.10.1 根因还在别处：日期基准指令被"诡计类型"挡住了（第二次修）**

9.10 上线后立刻被下一轮真实生成打脸：1996 长沙·湘绣厂那轮，大纲**明明给了** `caseDate="11月8日"`，
**6 个角色里 5 个却各自编日期**（11月19／27／13／17日…），修订要为此打 **37 条补丁**去统一。
而前一轮川剧团（时间诡计）日期一次就对。差别在哪？

查代码找到根因——那条"案发日期统一为「X」"的指令**写在 `buildTimeAxis()` 里面**：

```js
function buildTimeAxis(outline) {
  const off = parseTimeOffset(outline);
  if (!off) return "";                 // ← 非时钟类诡计：直接返回空串
  ...
  if (caseDate) L.push("案发日期统一为「…」");   // ← 于是这段话也只有时钟类诡计能拿到
```

**密室类诡计的角色从来没收到过这句话**，冷库/湘绣厂这类剧本全都如此。
**指令的作用域应当由"这条事实是否普遍成立"决定，而不是由"诡计类型"决定。**

**改法**：把日期基准移进 `buildSharedFacts()`（每个角色、含 NPC 都会拿到的那段共享事实），
与死亡时刻禁令并列；`buildTimeAxis` 里那份保留（时钟类场景另有用处，重复一句无害）。

**验证**：单测新增 3 项（有案发日必须写明且不含时钟类内容、缺日期时退化为相对表述禁令、
死亡禁令与日期基准并存）；并用**非时钟类诡计**的真实一轮复验。**A/B 干净对比（同为密室诡计）**：

| 指标 | 修前 1996 长沙·湘绣厂 | 修后 1994 郑州·棉纺厂 |
|---|---|---|
| 大纲 caseDate | 11月8日 | 11月17日夜至11月18日晨 |
| 诡计类型 | 密室 | 密室 |
| **交叉校验首条是日期问题** | **是**（"六个角色五套日期"） | **否** |
| **留档补丁里"日期被改写"** | **37/40** | **2/19** |
| 确定性体检 日期一致性 | **na（判不了）** | **ok** |
| 修订总补丁数 | 83 条 | 18 条 |
| 成稿日期分布 | 五个日期并存 | 11月17日×40、11月18日×28（+合法的前情 11月14–16日） |

> 这一条与 9.10 合起来说明了同一件事：**"全局唯一事实"要钉在源头，而且钉的位置必须是
> "所有角色都会读到"的地方**——先钉错位置（钉在大纲字段里，但读取端只认严格格式），
> 再钉错位置（钉在只有时钟类诡计才会走到的分支里），两次都是靠**真实运行的产物**才发现的。

## 10. 管理端"推理链"实时可视化

**问题**：诡计定稿器产出的不只是一句话诡计，而是一条**可校验的推理链**——
机制 → 物理可行性 → 目击条件 → 最弱处 → 证明链（每条线索各自能推出什么）。
但这条链此前只存在于内存里的 `report.trickDesign`，管理端**只看得到一行进度文字**
（"核心诡计已定稿并通过校验：…"）。三锁覆盖、物理可行性、最弱处全看不到，
而这恰恰是复核"这个诡计靠不靠得住"的全部依据。

**改法**（复用既有 `outline_done` 那套上报机制，零新增通道）：
1. `buildMurderMystery` 在诡计定稿后 `onProgress("trick_done", JSON.stringify({...design, attempts, lastErrors}))`；
2. `routes/admin.js` 把它转成独立的 SSE `trick` 事件；
3. `frontend/src/lib/sse.js` 增加 `onTrick` 回调；
4. 新增 `frontend/src/admin/TrickPanel.jsx`，并在 `PipelinePage` 排在 `OutlinePanel` 之前
   （诡计先于大纲定稿）。

面板内容：核心诡计一句话（封蜡红）→ 运作原理/隐藏方式/破绽方向 → **三锁覆盖**
（动机/手法/机会各被哪几条线索支撑；时钟诡计自动多出「时间线」、身份诡计多出「身份」）
→ 物理可行性（为什么做得到 / 目击条件 / **最容易被识破的地方**）→ 证明链逐条
（类型标签 + supports 多值标签 + "能推出什么"）。
另外把 `attempts > 1` 显示成「第 N 次通过」而不是"一次通过校验"——
**一次通过与被退回重做，对"这个诡计靠不靠得住"是两条不同的信息**。

**验证（真实浏览器，非推断）**：无头 Chrome + CDP 驱动管理端后台跑真实生成，
等 `trick` 事件到达后面板出现、截图并**逐张看过**：
- 第 1 张（成都火锅店·不在场证明，7 条证明链、一次通过）：三锁卡"动机 1 条 #6 / 手法 3 条 #1#2#5 / 机会 4 条 #1#3#4#7"、绿标「齐备」、最弱处卡为封蜡红描边；
- 第 2 张（青岛帆船·时间诡计，6 条证明链、**第 2 次通过**）：**自动多出「时间线」锁卡**（条件项生效）、头部标签换成警示态的「第 2 次通过」、证明链 #1 的 `clock-anomaly`/`timeline`/`opportunity` 多值 supports 拆解正确。

`consoleProblems: []`——整条流程（含面板渲染）**零控制台报错与未捕获异常**。

**当时没做的（改动 4 的另一半）**：**落盘**——本节做的面板是实时的，刷新即失。
已在下节补上（中间产物持久化 + 详情页复用同一块面板）。

## 11. 中间产物落盘（改动 4 的另一半）

**问题**：第 10 节做的面板是**实时**的——`trickDesign / outline / crossCheck` 只在生成进程的内存里，
刷新即失。要"事后复核已入库剧本的推理链"，必须先让它们持久化。

**改法**（沿用本项目既有架构：**Redis 为主数据源，PG 为异步落库的持久备份**）：

1. **装配**（新增 `src/script/artifacts.js`，纯函数）：从 `report` 里挑出
   `trickDesign` / `outline` / `crossCheck.issues`，按确定性规则限体积（256KB 上限），
   缺字段/结构异常一律返回 null，**绝不抛错**；
2. **落盘**：`script-writer` 在保存成稿后写 `session:<sid>:artifacts`。
   ⚠️ 用**独立 key**而不是塞进 `session:<sid>` 这个 hash——`listSessions` 会对每个会话
   `hgetall`，几十 KB 的 JSON 放进 hash 会把剧本列表接口拖垮；`deleteSession` 一并清理，避免孤儿 key；
3. **随切分带走**：`splitScript` 读出来放进 `split:<sid>:meta`；
4. **入库**：`pg-sync` 解析后交给 `saveSplitScript`，写进新增的 `scripts.artifacts JSONB`
   （`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 幂等迁移——只改 `CREATE TABLE` 的话，已有部署补不上列）；
5. **详情接口**：`/api/admin/scripts/:id/split-view` 返回 `artifacts`
   （从 `meta` 里剥出来单独返回，否则 Redis 路径下那串原始 JSON 会在响应里出现两份）；
6. **复用面板**：`ScriptsPage` 的「切分预览」弹窗直接渲染同一块 `TrickPanel`，
   并在下方列出交叉校验问题——**这稿弱在哪，终于有据可查**。

**体积兜底是有优先级、且如实记录的**：超限时先丢 `outline`（最大、且可从成稿重建），
仍超限则把 `trickDesign` 精简为结论面并记下 `proofChainOmitted: N`，
最后才丢 `crossCheck`。界面会把"证明链已省略原 N 条"直接告诉使用者——**不假装数据完整**。

**验证（分三段，各有独立证据）**：

| 环节 | 证据 |
|---|---|
| 装配 | 单测 9 项（挑字段/纯函数不改原对象/体积兜底优先级/如实记录丢弃条数/异常入参不抛）；全量 **616/616** |
| 落盘链路 | 真实生成一轮（2003 重庆·缆车调度员，`ok=true`，13.9 分钟），日志 `[writer] 中间产物已落盘：trickDesign=有 outline=有 20.9KB`；随后用脚本走完整链路（Redis → 切分 → PG → 详情接口）**15/15 通过** |
| 真落库 | 直接查 PG：`octet_length=22041`，`artifacts->'trickDesign'->>'coreTrick'`、`jsonb_array_length(proofChain)=7`、`crossCheck.count=13` 都能用 JSONB 运算符查到——**不是详情接口从 Redis 兜底拿的** |
| 界面 | 真实浏览器（无头 Chrome + CDP）打开「剧本管理 → 切分预览」：面板与交叉校验 13 条正常渲染，**两张截图逐一看过** |

> 这一轮验证还暴露了我**自己验收脚本**的一个错误：`replace(/\\s/g,'')` 里的反斜杠被 JSON 转义成
> 「字面反斜杠 + s」，正则匹配不到"登 录"按钮，而那句 eval 又**无条件返回 `login-submitted`**，
> 把没点着按钮报成了成功。教训与第 8 节那条同源：**验收脚本本身也要能失败**，
> 否则它只是一段会打印"通过"的文字。

## 12. 改动 3：量过之后**否掉**的方案，与改做的替代品

### 12.1 否掉的：跨角色"相互证词"确定性检测

**动机**：上一轮 13 个交叉校验问题里约 8 个是跨角色/跨模块的（换班请求时间倒置、目击与行踪冲突、
尸体发现时间三方矛盾）。公共事实表（事件表/公共事件表/物件状态表）天然覆盖不到这些**私密时刻**，
所以想加一条确定性判据：A 的时间线说"T 时刻我和 B 在一起"，而 B 自己在 T 时刻被写在别处 → 硬矛盾。

**先量后上（这一步救了这次改动）**：拿真实产物（2003 重庆·缆车案，6 角色、13 个交叉校验问题）
写了**只做测量、不进产品**的探针，把每个候选都打出来人工核：

| 判据版本 | 命中 | 判定 |
|---|---|---|
| 宽松（连接词 + 名字） | 2 处 | **2/2 全是误报** |
| 收紧（必须"我+连接词+名字"或"名字+对我的直接动作"） | 1 处 | 0 处矛盾（该处两侧一致：谭志强 17:30 在维修间说"何静问我"，何静 17:30 也在维修间） |
| 第二形态（同一对之间各只有一条互动、时刻却差 >20 分钟） | 0 处 | — |

宽松版为什么全错：**"和/与"在中文里常常只是连接两个人的连词**——
"周世奎**和谭志强**交接""谭志强**和何静**一组"被读成了"我和谭志强在一起"，
而这两行实际是"我（在休息室）**听见/看见**他们在别处"。这是本项目第 7 次"规则比事实更绝对"。

**更意外的一击**：为核对，我把那条被判"时间倒置"的原文读了一遍——谭志强 17:30 那条明确写着
"罗大力**白天已托人捎话**提出顶班请求，换班细节他**晚上再到南站当面敲定**"，
与罗大力 19:00 的说法**完全一致**。也就是说**那条问题是校验器自己误报的**。
一个连"真问题"都数不准的检测器，没有理由上线 → **否掉**。
（与 8.13 撤掉 `checkDateAgreement` 同一性质：先证明它比现状更好，做不到就不带缺陷发货。）

### 12.2 改做的：让自动改写**可审计**

上面那次复核暴露了更实在的问题：**驱动定向修订的是一份 LLM 产出的问题清单，它有噪声；
而修订正是照着这份清单自动改写成稿——改了什么，事后查不到任何痕迹。**
我想核对"它对那条误报做了什么"时，只能看到一句"已应用 24 条补丁"。

于是把 `revision` 留档接进刚落盘的中间产物（与 `crossCheck` 同一套机制，不新增通道）：

- `reviseByCrossCheck(..., record)` 每轮留档：`{round, issueCount, issues, applied, skipped, patches:[{oldText,newText}]}`；
- **"为什么没改动"也要留档**：第一版只在"补丁成功应用"后记录，结果漏掉了最该被看见的情形——
  实测那一轮交叉校验报了 **12 个问题，修订却"未产出可用补丁"**（LLM 输出被 `max_tokens` 截断 → JSON 不完整），
  而留档里什么都没有。补上后，一条补丁都没产出、以及"补丁均无法在原文定位"这两种情形都会写明原因（`note`）。
  **审计要看的是原因，不只是数字。**
- `buildArtifacts` 收进产物（体积封顶：单条文本 600 字符、每轮 40 条补丁、最多 6 轮；
  超限时**最后才丢它**——它是"自动改写可复核"的唯一依据）；
- 剧本详情页用 diff 形式（`− 原文 / ＋ 改后`）逐条列出，人能直接看出**改对没改对**。

**这不是"再加一条会误报的规则"，而是把不可见的自动改写变成可复核的痕迹**——
在没有可信判据之前，先保证**人能看见**。

**验证（真实一轮 + 逐层查证）**：1975 西安·俑坑案那轮，交叉校验报 11 个问题，
修订第 1 轮**应用 76 条补丁**、第 2 轮**一条都没产出**——正好把两种情形都覆盖了。

| 环节 | 证据 |
|---|---|
| 留档产出 | 产物顶层多出 `revision`：第 1 轮 `applied=76 skipped=0`；第 2 轮 `applied=0` + `note=模型未产出可用补丁` |
| 真落库 | 直接查 PG：`jsonb_array_length(artifacts->'revision')=2`、`第1轮补丁=40`、`第2轮note=模型未产出可用补丁` |
| 接口 | `/api/admin/scripts/:id/split-view` 返回 `artifacts.revision`（2 轮，内容一致） |
| 界面 | 真实浏览器：详情页以 `− 原文 / ＋ 改后` 列出补丁（红/绿），第 2 轮的琥珀色提示可见；**截图逐项看过** |
| 单测 | 新增 3 项（留档保留、长文本截断、结构异常不抛、"为什么没改动"必须留住）；全量 **629/629** |

**留档立刻证明了它的价值**——以前只看到"已应用 76 条"，现在能读到具体动作，
例如它把 `4月16日` 统一成 `6月14日`（跨角色日期不一致），
并把"我把那半页纸贴身收了"改成"那半页纸还在他手里攥着"（修掉与凶手动机的自相矛盾）。

> ⚠️ 这一节的结论是"**不改**某件事"。它与第 9 节那些"改了并验证"的条目同等重要：
> 本项目已有三次"规则比事实更绝对"的教训（8.3.1 / 8.7 / 8.11.1），
> 而这次是在**写代码之前**就量出来并止住的。

### 12.3 修订后复检：确定性护栏 + 重新交叉校验

12.2 让自动改写**可被看见**了，但还剩两个洞：

- **两轮用同一份问题清单**：第一轮改完不复核，第二轮还拿**过期**的清单继续改——
  既不知道改好了没有，也可能把已经对了的地方改坏；
- **没有任何机器护栏**：改坏了只能靠人翻留档才发现。

**改法**：`reviseByCrossCheck` 增加 `opts.recheck` 回调，每轮改完回调一次，做两件事：

1. **确定性护栏（便宜、无 LLM）**：用**既有、已被信任**的判据给成稿做体检——
   跨角色日期一致性（`checkDateAgreement`）、第一轮线索是否指控真凶（`checkRoundUnlock` + `nameAccuses`）、
   死者死后仍在活动（`checkVictimAfterDeath`）。**任何一项从"通过"变"不通过" → 整轮回退**
   （留档写明原因）：宁可少改，不可把已经对了的地方改坏。
   *只用既有判据、不新增判断规则*，所以不引入新的误报面。
   ⚠️ 体检必须**从成稿本身切段**（新增 `extractCharacterSections`）——
   `report.characterScripts` 是生成期文本，修订之后与成稿已经不同步。
2. **重新交叉校验（贵，一次 LLM 调用）**：拿**新**的问题清单驱动下一轮；
   若复检已无问题就提前收工（省掉后续轮次）。复检结论（剩余问题数）也落盘——
   **它直接回答"改了到底有没有用"**。

单测新增 7 项（成稿切段含 `[凶手]` 标记处理、回退判据只判"通过→不通过"与"违规变多"、
`unknown`/`na` 不被当成"通过"、无 outline 不抛、死亡后活动可计数、体检结论与撤销标记留档、
复检剩余问题数留档）；全量 **644/644**。

**验证（真实一轮：1988 武汉·棉纺厂，`ok=true`，18.8 分钟）**——生产日志：

```
第 1 轮应用修订 19/19 条
第 1 轮修订后体检：日期一致性=ok、轮次解锁=ok、死亡后活动=0 处
第 1 轮修订后复检：剩余 9 个问题          ← 新清单驱动第 2 轮（原清单是 11 个）
第 2 轮应用修订 16/16 条
第 2 轮修订后体检：日期一致性=ok、轮次解锁=ok、死亡后活动=0 处
第 2 轮修订后复检：剩余 9 个问题
交叉校验定向修订完成：共应用 35 条
```

界面（截图逐项看过）：每轮都显示体检结论，末尾一行"复检结论：改写后交叉校验剩余 9 个问题"。
留档同时落到 Redis 与 PG（`jsonb_array_length(revision)=2`、`revisionRecheck.count=9`、`verdict.dateAgreement='ok'`）。

> **⚠️ 这一改的第一版结论是错的，被自己验掉了——过程值得留存。**
> 看到"11 个问题 → 改 35 条 → 仍然 9 个问题"，我写下"**自动修订不收敛**"。
> 但在把它当结论之前，我先去量了另一个解释：**交叉校验本身可复现吗？**
> 拿**同一份**最终成稿连读两遍（各 10 个问题、分别 56s / 40s），两批问题**只有 2/10 能对应上**
> （相似度阈值 0.25）。也就是说**校验器是不可复现的 LLM 抽样**——
> "11 → 9"的差别落在噪声里，**"不收敛"这个结论不成立**；同样，"修订把 11 个全修好了"
> 也不能由此得出。凡是"拿两次交叉校验结果对比"的推论（不论方向）都不可靠。
>
> 由此**改掉了自己交付物里的一处过度宣称**：详情页原本写"复检结论：改写后交叉校验剩余 9 个问题"，
> 现在改为如实标注它是**抽样**、并写明"同一份文本连读两遍也只有约 2/10 能对应上，
> 这个数字不能当作'改好了没有'的判据"。
>
> **那么这次改动真正立得住的价值是什么**（与上面那条无效推论区分开）：
> ① **确定性护栏**（日期一致性／轮次解锁／死亡后活动）是**可复现**的判据，不依赖 LLM 抽样——
>    它是"改坏了没有"唯一可信的机器判据；
> ② 第 2 轮拿到的是**当前文本**的清单，而不是改写前那份已经过期的清单（方向正确，只是清单本身有噪声）；
> ③ 每条 patch 的原文留档，人能逐条看。
>
> **顺带得到的线索（后被自己量掉）**：既然单次抽样重合率低，我提出"**读两遍取交集**作为高置信问题"。
> 但在写代码前先量了它，做法是**对同一份成稿连读 4 次**（27s/33s/34s/32s），结果是：
> **`0 / 11 / 8 / 9` 个问题，两两重合率 0%**（四字片段相似度阈值 0.25）。
> 也就是说：交集≈空集，**取交集会让修订几乎什么都不改**——高精度换来的是几乎为零的召回。
> **该方案否掉，未写进产品代码。**
>
> 更值得记的是**这次测量还顺手抓到一个真缺陷**：4 次读里有 1 次报了 **0 个问题**，
> 而同一份文本另外三次报了 8~11 个。查代码发现——`extractJsonStrict(result.content) || {}`
> 让**解析失败**得到空对象 → `issues=[]` → 对外表现为"**校验通过、零问题**"，
> 而实际上这次校验**根本没有结论**。更危险的是它会传导到 12.3 刚加的复检：
> 复检若解析失败会拿到空清单，进而**静默跳过后续修订**（把"校验失败"变成"提前收工"）。
> **已修**：① 解析失败显式标记 `parsed:false` 并**重试一次**；② 复检没有结论时**沿用原清单继续**
> 而不是当成"没问题"；③ 留档与界面都区分"没有结论"与"0 个问题"。

> **⚠️ 同一轮里我还写过一个更错的结论，被自己验掉了（第三次）。** 看到交叉校验报
> "何秀云按 **11月19日**、罗美凤按 **11月27-28日**…六个角色五套日期"，我到**改后**的成稿里逐个查，
> 发现这些日期**一次都没出现**，于是判定"**校验器在编造具体事实**"，还据此写了一个
> "核查问题是否有据"的过滤器（`verifyIssueGrounded`）。
>
> 上线前我去核了替代解释：**留档里的补丁**。结果 40 条留档补丁里有 **37 条**正是
> `11月19日 → 11月8日`、`11月18日 → 11月7日` 这样的日期统一——
> **那些日期在改前确实存在，校验器说的是对的**，是**修订把它们改掉了**，所以在改后文本里当然找不到。
>
> 若当时上线那个过滤器，它会把这些**正确的修复依据**判成"无据"丢掉——恰好造成它本想防止的伤害。
> **过滤器已删除**（连带那套纯函数），理由记在此处。
> 教训：**用"改后"的文本去核"改前"的问题，结论必然是错的**；而 12.2 做的留档
> 这次正好成了判定这件事的唯一依据——**留档的价值在这一刻从"给人看"变成了"给判断用"**。

⚠️ 这一轮还顺带抓到一个**我自己修复里的缺口**：大纲给的是跨午夜区间
「5月17日夜至5月18日晨」（对这种案件比单日更准确），而读取端只认严格 `X月X日` → 判非法 → 回退 null，
于是新加的告警响了、角色又被告知"严禁自创日期"。**是那条告警把这层缺口暴露出来的**（否则只会表现为
"这一轮日期怎么又乱了"）。已修：接受区间写法并取第一段作案发当日（次日由既有 `nextDayLabel` 推出），
提示词里也写明允许该写法。

### 12.4 截断抢救：让"整轮白跑"不再发生，"判不了"要说出来

**问题（实测）**：定向修订的输出被 max_tokens 截断时，`extractJsonStrict` 返回 null
（它的括号扫描要求成对闭合，截断时 depth 回不到 0），而调用方写成 `extractJsonStrict(...) || {}`
→ 得到 0 条补丁 → **整轮白跑**，留档只写一句"模型未产出可用补丁"——看不出其实是"输出被截断"。
而截断前往往已经写好了若干条**完整**补丁。上一轮给交叉校验加过"解析失败就重试一次"，
但截断多半会复现，重试常常无果。

**修法**：
1. 新增纯函数 **`repairTruncatedJson`**（json-extract.js）：在每个"结构完整"的闭合括号处切点，
   丢掉没写完的半截元素，补齐还开着的括号后尝试 parse，取**最长**能成功的那个；救不出就返回 null
   （**绝不假成功**——半条补丁会带着残缺的 newText 溜进 `applyPatches`，造成错误改写）。
2. 修订的补丁获取改为三段：正常解析 → **截断抢救**（比重试便宜）→ 仍拿不到再重试一次；
   三种结局**分别记账**（"模型未产出补丁（patches 为空）" / "补丁 JSON 解析失败（本轮白费）"），
   抢救来的补丁在留档与界面都标出"补丁是从截断输出里抢救来的（N 条）"。
3. 交叉校验同样改为"解析 → 抢救 → 重试"；抢救得到的清单会标注"输出被截断，问题清单可能不全"
   （每条可能是真的，但清单本身不全——必须说出来）。

**验证**：
- 单测 **9 项**（新建 `tests/unit/json-extract.test.js`）：先钉住"截断时 `extractJsonStrict` 必须返回 null"
  （这是整轮白跑的根因），再钉住抢救行为——半截元素整条丢掉、完整输出原样返回、
  字符串里的花括号与转义引号不制造假切点、救不出来返回 null、多层嵌套也能切干净。
- **真实数据**：把真实产物里的 **19 条补丁**按模型格式拼成 JSON，在几十个位置截断——
  **每个截断点救回的都是原件前缀，逐条逐字一致，从未产出半条**；截掉末尾 1/3 能救回 **12 条**（修前 0 条）。

**"判不了"必须出声音**：`checkDateAgreement` 证据不足时返回"不需要判定"，此前流程里**静默**通过——
1996 长沙那轮交叉校验第一条就是"六个角色五套日期"，而确定性体检只能给 `na`。
现在：流程里告警"证据不足，这一项本次没有把关"；界面把 `na` 显示成
**"无法判定（证据不足，没把关）"**，不再让一个看起来像正常态的字面值掩盖"根本没检查"。

> 顺带记两个**自己写的夹具/校验**的错（都没进产品代码）：
> ① "完整输出"夹具的两条补丁之间**漏了逗号**，那份 JSON 本身非法，函数按截断只救回 2 条；
> ② 真实数据校验里用 `oldText` 去原件配对，而真实补丁里存在 `oldText` 相同的两条 → 误报"半条"。
> **正确不变式是"救回的必须是原件前缀，按下标逐条比"**。
